## 1. 정상 구동 확인 (`scripts/smoke.py`, 결과 `runs/smoke-20261127-032853/`)
[측정] 시나리오 S2~S5 입력을 화면 대신 API로 한 번씩 보냈다. 앱 코드는 고치지 않았다.

| 앱 | 결과 |
|---|---|
| A | 문장 읽기 4건 모두 HTTP 200(2~6초). 복기 S2·S3·S5 모두 결과까지 나옴. S4 없는 이름은 누락 칸(`my_form_key`, `move_key`)으로, 면역 조합은 누락 칸(`actual`)으로 응답. 빈 입력은 422 |
| B | S3(대면 판단)는 `ok`. S4 없는 이름은 후보를 제시하는 `ask`. **S2·S4 빈 팀·S4 5마리는 `UPSTREAM_ERROR`** |

**[측정] B의 `UPSTREAM_ERROR` 원인은 Gemini 무료 한도다.** 같은 시각 직접 호출한 결과가 HTTP 429였고, 한도 항목은 `GenerateRequestsPerDayPerProjectPerModel-FreeTier`, **limit=20**이었다(모델 표기 `gemini-3.6-flash`, 다음 초기화까지 약 4.5시간). 외부 데이터 API 문제가 아니다. Windows 세션이 본 같은 오류도 이 한도였을 가능성이 높다[해석].
- B는 LLM 오류를 모두 `UPSTREAM_ERROR`(LLM 서버가 정상 응답하지 않음)로 묶어 보여 준다(`backend/app/agent/llm.py`). 앱 동작이므로 고치지 않고 기록만 한다.
- 같은 날 앞서 S2가 정상 동작한 기록이 있다(선출·스피드·데미지까지, 약 26초).
- S5가 "내 포켓몬을 알려주세요"로 되물은 것은 같은 대화의 S2가 실패해 팀이 기억되지 않았기 때문으로 보인다[해석]. 한도가 남은 상태에서 다시 확인한다.

## 7. (8절로 대체됨) Gemini 판정 = flash-lite 7 : flash 3
- **회차 단위로 나눈다.** 한 회차는 절대 평가 X·Y + 쌍비교 XY·YX 4건이다. 건 단위로 나누면 한 모델이 특정 순서·앱을 더 받아 위치 편향 측정과 앱 비교가 섞인다.
- 3회차로는 7:3이 나오지 않아 **Gemini만 10회차**로 늘렸다: `gemini-3.5-flash-lite` 7회차(28건), `gemini-3.5-flash` 3회차(12건). 회차 배정은 섞는다(flash = 2·5·9회차, 나머지 lite). Claude·OpenAI 판정은 3회차 그대로.
- 설정: `.env`의 `JUDGE_GEMINI_PLAN=gemini-3.5-flash-lite:7:6,gemini-3.5-flash:3:20` (모델:회차수:호출 간격 초). 확인: `python judges/judge.py --plan`.
- 원본은 `judges/raw/gemini.jsonl` 한 파일, 레코드마다 `judge_model`이 남는다.
- **집계 방식 변경:** 판정 모델(공급사)마다 회차 수가 달라 ALL 값은 판정 모델별 값의 **단순 평균(동일 가중)**이다. 그냥 합치면 Gemini 40건이 결과를 좌우한다. `gemini:<모델>` 세부 행은 따로 남기고 ALL에는 넣지 않는다. ALL의 `abs_sd`는 "판정 모델 평균들 사이의 표준편차", 판정 모델별 `abs_sd`는 "회차 간 표준편차"다.
- 시험: `tests/test_pipeline.py` 13개 통과(7:3 배정, 모델별 X/Y·XY/YX 균형, 동일 가중, 세부 모델 행 포함).
