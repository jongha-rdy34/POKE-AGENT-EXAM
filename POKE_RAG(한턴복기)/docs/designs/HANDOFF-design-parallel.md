# 인계장: 디자인 병렬 작업 (2026-10-23, 서버 완성 후)

받는 사람: 디자인 에이전트(별도 세션). 보낸 쪽: 엔지니어링 세션. 이 인계장은 작업 지시서이고, 판단은 받는 쪽이 한다.

## 지금 상태

- **복기 서버는 동작한다.**
  - 코드는 `server/app.py`이다. 실제 GMS로 확인했다: 문장 읽기 약 4.6초, 복기 약 2.1초.
  - API 계약은 `agent.md` 1.2절 표와 같다.
- **엔지니어링 세션은 동시에 `web/`을 만든다.**
  - `web/`은 시안 `prototype/review-tab.html`을 실제 API에 붙인 화면이다.
  - 디자인 쪽은 `web/`·`server/`·`prep/` 파일을 고치지 않는다. 같은 파일을 동시에 고치면 충돌한다.
  - 디자인 결과는 `docs/designs/prototype/review-tab.html`(또는 새 시안 파일)과 이 폴더의 문서에 남긴다.
  - 엔지니어링 세션이 그 결과를 `web/`으로 옮긴다.
- **실제 응답 예시는 `docs/designs/samples/`에 있다.** 시안의 예시 데이터를 이 값으로 바꿔서 보면 된다.

| 파일 | 상황 |
|---|---|
| `extract-review.json` | 문장 읽기 성공. `ask`(꼭 다시 확인할 칸)와 `notes`, 화면용 이름(`labels`) 포함 |

응답에서 시안과 달라진 점:
- 원인에 %나 확률이 없다. `rank`(순위), `rolls`("가장 그럴듯한 조건에서 16번 중 k번"), `rolls_k`(난수 띠에 칠할 칸 수), `conditions`(한글, 최대 3개)만 있다.
- 성립 조건은 이런 형식이다: "장난꾸러기 · H32 B32 · 특성 지구력 · 도구 없음·영향 없는 도구". 마지막 묶음은 "공격 −1" 후보일 때만 붙는다.
- 요약 문장(`summary`)은 서버가 만든다. 코드가 사실 문장을 쓰고 LLM은 다듬기만 한다.
- `degraded: true`이면 LLM이 다듬지 못해 코드 문장을 그대로 보낸 것이다.

## 병렬로 할 일 (우선순위 순)

### P0. 계산표 (개정 v1.4, 2026-10-23 추가 — 가장 먼저)
- **무엇:** 결과 화면에 새로 생긴 "계산 결과 · 상대 빌드별" 표.
  - 위치는 결론 바로 아래, 통계 원인표보다 위다.
  - 응답의 `calc`에 들어 있다. 예시는 `samples/review-friend1-calc-first.json`(친구 사례: 빠르모트 냉동펀치 → 메가한카리아스Z)이고, 다른 review 예시에도 모두 `calc`가 있다.
- **한 줄의 내용:**
  - 빌드 이름(`label`, 예: "A32 · 고집 · 특성 철주먹 · 생명의구슬")
  - 결과("16번 중 k번 (pct%)") + 난수 띠(`k`)
  - 데미지 범위(`damage`, HP 대비 %)
  - 같은 결과 도구(`same_items`)
  - 통계 표기(`usage`, 예: "pokedb M-6 이 포켓몬 생명의구슬 채용 31%")
  - `in_champions: false`이면 "챔피언스에 없는 도구" 표시
- **그 밖의 칸:**
  - 스피드 결과는 `speed` {opp, me}이고 `k`는 없다.
  - 결과가 나오는 빌드가 없으면 `rows`가 비고 `near`(가장 가까운 빌드)가 온다.
  - `my_build`는 계산에 쓴 내 빌드이고, `assumed`는 상대 SP 가정 문구다.
- **정할 것:**
  - 표 모양. 시중 계산기(스마트누오)처럼 읽혀야 한다.
  - "챔피언스에 없는 도구" 줄을 흐리게 할지, 따로 묶을지.
  - 폰 폭에서의 배치.
  - 통계 원인표와의 관계. `web/`에는 지금 "통계로 보면" 제목 아래 원인표를 두었다.
- **바뀐 원칙:** 계산표의 난수 %는 계산 사실이라 보인다(C-O1 부분 변경). 원인 확률 %는 여전히 숨긴다.

### P1. 두 기준 나란히 보기 (D31·D32, 기존 인계장 미반영분)
- **언제:** `differs: true`.
- **무엇을:** 원인 표를 pokedb(실제 랭크배틀)와 Smogon(Showdown 시뮬레이터) 두 묶음으로 보여 준다.

  - 출처 링크는 `bases.smogon.source.url`.

- **`diff_reason`:** 사용자에게 보일지, 보인다면 문구를 정한다. 예: "두 기준의 내 빌드 가정이 달라 생긴 차이일 수 있음".
- **폰 폭(<600px):** 나란히가 안 되면 위아래로 쌓는다.

### P1. 확인 화면의 "꼭 확인" 칸과 안내 문장
- **`ask`:** 값이 들어 있는 칸 이름 목록이다. 예: `["move_key"]`, `["actor"]`, `["actual"]`.
  - 값은 채워져 있지만 사용자가 다시 봐야 한다. 기존 빈 칸(`.chip.missing`)과 다르게 보이는 표시가 필요하다.
- **`notes`:** 한국어 안내 문장이다. 예: "문장에서 기술 '드래곤애로'를 찾았어요. 맞는지 확인해 주세요". 확인 문장 아래 어디에 둘지 정한다.
- **`missing`:** 빈 칸이다. 지금 시안은 칩에 `missing` 표시를 하고 "이대로 복기" 버튼을 막는다. 그대로 써도 되는지 확인한다.

### P1. 추출 실패와 서버 상태 문구
`errors-and-states.json`의 각 상황에 맞는 화면 문구와 위치를 정한다. 지금 시안에 있는 것은 403 전체 화면과 횟수 소진 문구뿐이다.

| 상황 | 의미 |
|---|---|
| 추출 `llm_unavailable` | 키 없음·서버 오류 → 직접 입력 |
| 추출 `empty`·`broken_json`·`refusal` | 문장을 이해 못 함 → 직접 입력 |

| 429 `token_limit` / `server_limit` | 내 횟수 소진 / 서버 전체 소진. 문구가 서로 달라야 한다 |
| SSE `bad_input` / `internal` | 입력 오류(조건 고치기로) / 서버 문제(다시 시도) |
| `degraded: true` | 계산은 정확하고 문장만 기본형이다(시안의 기존 문구 재사용 가능) |
| `bases` 비어 있음 | 바디프레스처럼 계산하지 않는 기술. 결론 대신 `unsupported`를 보여 준다 |

### P0. 계산표

순서: 결론 h1 → 가정 줄 → **`section.calc` "계산 결과 · 상대 빌드별"** → `h2.section-title` "통계로 보면" + 한 줄 설명 → 두 기준 묶음 → 접힘·"진짜 패인?".

- **구역 제목** `h2.section-title`(22px·700, 위 1px `line` + 위 여백 32px): "계산 결과 · 상대 빌드별", "통계로 보면". 결론(26px) 바로 아래 단계다. 기준 제목(`h3.basis-head`, 16px)은 그 아래다. 기준 제목은 h2에서 **h3로 바꿨다.**
- 제목 아래 `p.basis-src`: "내 빌드 {`my_build`} · {`assumed`}". "통계로 보면" 아래: "상위 사용자들이 실제로 많이 쓰는 빌드로 좁혀 본 원인이에요".
- **한 줄**(`ol.calc-rows > li`, 시중 계산기처럼 데미지 범위가 먼저 눈에 띈다):
  1. `p.calc-label` 빌드 이름(`label`, 14px·500)
  2. `p.calc-line`(flex, 폰에서 줄바꿈): `span.calc-main` **데미지 범위** "84.3~100%"(16px·700, 최소 폭 8.5em로 띠 위치를 맞춤) + 난수 띠(`k`) + `span.calc-res` 결과(14px)
  3. `p.calc-meta` 통계 표기(`usage`) + "같은 결과: {`same_items`}"를 " · "로 이어서(14px `muted`)
- **결과 문구**(계산기 용어):
  - 한 방(`ko`): `k`=16 "확정 1타", 0 "1타 불가", 그 밖 "난수 1타 · 16번 중 k번 (pct%)"
  - 버팀(`survived`): "16번 중 k번 이 HP로 버팀 (pct%)"
  - 스피드(`speed`, `k` 없음): 큰 글씨 "상대 319 · 나 169", 결과 "상대가 먼저" / "내가 먼저" / "동속(먼저 움직이는 쪽은 무작위)". 띠 없음.
  - pct는 소수 한 자리까지, 끝의 .0은 뺀다(75.0 → 75%). **계산표의 %는 계산 사실이라 보인다**(엔지니어링이 적은 C-O1 부분 변경). 통계 원인표에는 여전히 %가 없다.
- **챔피언스에 없는 도구**(`in_champions: false`): 흐리게 하지 않는다. 표 아래 `h3.calc-group` "챔피언스에 없는 도구" + `badge` "참고" + 설명 "지금 챔피언스에서는 쓸 수 없는 도구예요. 상대 빌드를 잘못 짐작했을 수 있다는 신호로 보세요" 아래에 따로 묶는다. 친구 사례처럼 이 줄이 결과(12/16)를 설명하는 경우가 있어서, 흐리게 하면 그 신호를 놓친다.
- **줄 수:** 챔피언스에 있는 빌드는 처음 3줄만 보이고, 나머지는 바로 아래 `details.calc-fold` "빌드 N개 더 보기"로 접는다(폰에서 6줄이면 통계 구역까지 2화면 넘게 내려가야 했다). `more`가 있으면 "결과가 비슷한 빌드 N개는 생략했어요".
- **결과 없음**(`rows` 빈 배열): `p.calc-empty` "이 결과가 나오는 상대 빌드가 없어요. 가장 가까운 빌드를 보여 드려요" + `near`를 같은 줄 모양으로. (`near`의 줄 형식이 `rows`와 같다고 가정했다. 다르면 알려 달라.)
- **띠 색:** 결론(`headline`)이 가리키는 줄 = `rows` 중 챔피언스에 있는 첫 줄의 띠만 청록(`li.lead`). 나머지 계산표 띠와 통계표 띠는 모두 `roll`. `near`(결과 없음)·스피드(띠 없음)면 청록 없음(2026-10-23 web/ 검수 W3, 사용자 결정).
- `calc: null`(계산 안 하는 기술)이면 구역째 없다.
- **결론 문장 예시(제안 `headline`, 계산 기준):** "챔피언스에 있는 도구로는 16번 중 1번만 한 방이에요"(친구 사례), "상대가 고집 달인의띠면 16번 중 12번 한 방이에요", "상대 드래펄트는 도구 없이도 내 한카리아스보다 빨라요". 시안 `SAMPLES.*.headline`에 손으로 넣어 두었다.

### P1. 두 기준 나란히 보기

- **`differs: true`** → `.bases` 안에 우선순위 순서로 `section.basis` 두 개: 먼저 pokedb(주 기준), 다음 smogon(`section.basis.sub`, 제목 끝 " (참고)"). **반응형**(사용자 지시 2026-10-23):
  - **화면 1200px 이상:** 좌우 배열. 이 영역만 720px 본문 밖으로 넓혀 1104px(`width: 1104px; margin-left: calc((100% - 1104px) / 2)`), 두 열 536px, 열 사이 32px + 오른쪽 열 왼쪽 1px `line` 구분선. 원인 행은 PC 한 줄 배치(순위 | 도구·조건 | 띠+글자) 그대로.
  - **1200px 미만:** 상하 배열. 아래 기준은 위 여백 32px + 2px `line` 구분선으로 뗀다. 원인 행은 PC 배치, 폰(<600px)은 3줄 배치.
  - **720px 본문 안 두 열은 쓰지 않는다.** 열이 340px쯤이라 조건이 단어 단위로 끊긴다(web/ 2026-10-23 화면에서 확인).
  - 좌우 배열은 화면 코드가 `differs`일 때 `.bases`에 `two` 클래스를 붙이고 `@media (min-width: 1200px) { .bases.two { … } }`로 한다(E8 합의: `:has()`는 친구 기기 브라우저 지원을 확인하지 못해 배치에 쓰지 않는다).
  - `h2.basis-head`: "실제 랭크배틀 기준" / "Showdown 시뮬레이터 기준 (참고)" (16px·700)
  - `p.basis-src`: `source.label`. Smogon은 둘째 줄에 `source.note` + " · " + [출처](`source.url`). **항상 보인다**(접지 않음). 색은 `muted`. 경고색이 아니다: 경고색은 참고용·저하 전용이다(DESIGN.md).
  - smogon 묶음의 출처 줄 바로 아래 `p.diff-note`(14px, `text` 색): "이 기준에서는 결과가 달라요. 데이터를 모은 곳과 내 빌드 가정이 달라서일 수 있어요"
- **`differs: false`** → `.bases.one`(pokedb 한 열) + 아래 `details.fold.other-basis` 접힘 "다른 기준(Showdown 시뮬레이터)으로 보기". 펼치면 같은 `section.basis`(시뮬레이터 표기 포함).
- **`diff_reason`은 화면에 내지 않는다.** 영문 키("expert-belt")와 내부 표현("한쪽만 일치 0건")이 섞여 있어서다. 위 고정 문구 한 줄로 대신한다. 기록용으로만 쓴다.
- **통계 원인표에는 청록을 쓰지 않는다**(2026-10-23 web/ 검수 W3, 사용자 결정). 청록은 결론이 가리키는 계산표 줄에만 둔다(P0 "띠 색"). 한 화면에 답은 하나다.

### P1. 확인 화면 "꼭 확인" 칸과 안내 문장

- `ask` 칸 → `.chip.check`: 값은 그대로(굵게, `chip` 배경) + **`warning` 1px 실선 테두리** + 칩 안 꼬리 `span.chip-tag` " · 확인"(14px, `warning`). 빈 칸 `.chip.missing`(오류색 점선, 굵기 400)과 선 종류·색·굵기가 모두 다르다.
  - "이대로 복기"는 막지 않는다(값이 있으므로).
  - 사용자가 그 칩을 누르면 표시를 지운다(시안: `st.ask`에서 뺌).
  - 서버 칸 이름 → 칩: `my_form_key`→내 포켓몬, `opp_form_key`→상대 포켓몬, `move_key`→기술, `actual`→결과, `actor`→공격한 포켓몬 칩.
- `notes` → `ul.extract-notes#extractNotes`: 칩 줄 바로 아래, 원문 인용 위. 14px, `text` 색, 글머리표 없음.
- `missing` → 지금 방식 유지: `.chip.missing` + "이대로 복기" 비활성 + 버튼 아래 이유 한 줄(`#goReason`, 예: "기술을 골라 주세요").

### P1. 추출 실패·서버 상태 문구

문구는 서버 `code`로 고른다. 서버 `message`는 아래 표에 없는 code일 때만 그대로 쓴다.

| 상황 | 화면 문구 | 위치·모양 |
|---|---|---|
| 빈 문장(`empty_input`, 클라이언트) | 무슨 일이 있었는지 한 줄 적어 주세요 | 자연어 칸 아래 `#nlStatus.hint.danger` |
| 추출 `llm_unavailable` | 지금은 문장을 읽을 수 없어요. 아래 칸을 직접 채워 주세요 | `#nlStatus.hint.warn` + 「더 정확하게」 펼침 |
| 추출 `empty`·`broken_json`·`refusal` | 문장을 이해하지 못했어요. 아래 칸을 직접 채워 주세요 | 같음 |
| 추출 `rule` | 규칙 질문 답변은 아직 준비 중이에요. 실제로 있었던 한 턴(누가 어떤 기술로 어떻게 됐는지)을 적어 주시면 복기해 드릴게요. / 한 턴을 복기하려던 거예요? [복기로 바꾸기] | `#ruleView` (web/ 문구 그대로 채택) |
| 429 `token_limit`(문장 읽기) | 오늘 이용 횟수를 다 썼어요. 내일 다시 이용해 주세요. 입력한 내용은 그대로 있어요 | `#nlStatus.hint.warn`. 문장 읽기 한도는 복기와 따로라 "복기 횟수"라고 쓰지 않는다(E5 ②) |
| 429 `token_limit`(복기) | 오늘 복기 횟수를 다 썼어요. 내일 다시 이용해 주세요. 입력한 내용은 그대로 있어요 | 결과 자리 `h1.notice.warn`, 버튼 없음 |
| 403 `no_token`(어느 API든) | 초대 링크로 접속해 주세요 | 전체 화면 초대 안내(상태 16). 검색·기술 목록·남은 횟수 API의 403도 같다(E5 ③) |
| 피드백 `{"ok": false}` | 기록하지 못했어요. 결과는 그대로 볼 수 있어요 | "진짜 패인?" 버튼 아래 `#fbStatus.hint.warn`. 버튼은 그대로 둬 다시 누를 수 있다(E5 ④) |
| 429 `server_limit` | 오늘은 서버 사용량이 다 차서 복기할 수 없어요. 내 횟수와는 관계없어요. 내일 다시 이용해 주세요 | 같음 |
| 422 (HTTP 상태로 고름, `code` 없음) | 입력한 조건을 처리하지 못했어요. 조건을 고쳐 주세요 | 결과 자리 `h1.notice.danger` + [조건 고치기](주 버튼). FastAPI 기본 형식이라 `detail`은 화면에 내지 않는다(E5 ①) |
| SSE `bad_input` | 입력한 조건으로는 계산할 수 없어요. 조건을 고쳐 주세요 | 같음. 서버 message("알 수 없는 기술: no-such-move")는 영문 키라 화면에 내지 않는다 |
| SSE `internal` | 계산 중 문제가 생겼어요. 잠시 뒤 다시 시도해 주세요 | 결과 자리 `h1.notice.danger` + [다시 복기](주 버튼) |
| 연결 끊김 | 연결이 끊겼어요. 입력한 조건은 그대로 있어요 | 같음 + [다시 복기] |
| `degraded: true` | (안내 없음) | 2026-10-23 web/ 검수에서 변경: 결론(`headline`)·계산표는 코드가 만들고 LLM이 다듬는 `summary`는 화면에 나오지 않는다. 안내를 두면 보이지 않는 문장을 경고하게 된다 |
| `bases` 비어 있음 | 결론 h1 = 서버 문장, 아래 `unsupported`를 경고색 한 줄 | 띠·접힘·"진짜 패인?"·U7 없음. [조건 고치기]가 주 버튼 |
| 남은 횟수 | 오늘 남은 복기 N번 | `quotaLine()`: `remaining.review` ≤ 5일 때만, 복기하기 버튼 아래 `#quotaLine.hint` |

- 오류 문구는 그 화면의 결론이라 `h1`(22px)이다. 화면당 h1 하나 규칙(DESIGN.md).
- 자연어 칸에 `maxlength="300"`을 걸었다(422 문장 길이 예방).

### P2. "도구로 구분 불가"(`undetermined: true`)

- 표는 접지 않는다. 띠가 "어느 도구든 결과가 같다"는 것을 직접 보여 주기 때문이다.
- `ol.causes.flat`: **순위 숫자 없음, 청록 없음.** 캡션 "상대 도구로는 구분하기 어려워요. 아래 후보 모두 이 결과와 맞아요".
- 기준별로 판단한다(한쪽만 구분 불가일 수 있음, 예: 22번 급소 샘플).

### P2. 정리

- "예상했던 결과" 칸: 시안에서도 뺐다.
- 채팅(`#chatView`): 시안에서 뺐다. 추가 질문 버튼(채팅으로 보내던 것)도 뺐다. 예시 문장 "규칙 질문" 버튼도 뺐다(준비 중 화면으로만 가므로). 확인 단계의 "규칙만 궁금해요 · 질문으로 바꾸기"도 뺐다.
- 근거 접힘 → **"가정 · 계산하지 않은 것 · 출처"**: 가정 = `assumptions` + 기준별 `notes`("실제 랭크배틀 기준: …" 접두), 계산하지 않은 것 = `unsupported`, 출처 = 기준별 `source.label`(+ `url`이 있으면 [원문]). 결론 옆 "근거 N" 링크는 없앴다.
- 진행 표시: 서버 SSE가 `status: computing` 한 번뿐이라 3단계 목록 대신 한 줄 `p.progress` "계산하는 중…".
- 원인 행: 띠 옆 글자는 "16번 중 k번"으로 줄이고(`rolls_k`), "가장 그럴듯한 조건에서 …"는 결과 아래 `p.roll-legend` 한 줄로 한 번만 쓴다. `rolls_k: null`(행동 순서)이면 띠·글자 없음. 조건은 `conditions[0]` + " 외 N개".
- `excluded_share`는 반올림해서 1% 이상일 때만 안내한다(0%로 보이지 않게).

### 엔지니어링에 제안 (서버 쪽, 디자인이 고칠 수 없는 것)

1. **`headline` 필드 추가.** `summary`는 두 기준 문장 + 미계산 항목이 이어져 26px 결론 제목으로 쓰기에 길다(3~4줄). 주 기준(pokedb) 한 문장, 괄호 속 난수 없이. 예: "이 타격은 내 공격이 한 단계 내려가 있었을 때 가장 잘 맞아요". 시안 샘플에 손으로 넣어 두었다(`SAMPLES.*.headline`). 없으면 `summary`로 대신한다.
2. **영문 키를 한글로.** 화면에 나가는 문자열에 영문 키가 남아 있다:
   - `bases.*.notes`: "nature=adamant, item=choice-scarf, ability=sand-veil", "sp={'hp': 32, …}"
   - `unsupported`: "계산하지 않은 상대 특성: sturdy", "…: body-press"
   - SSE `bad_input` message, `diff_reason`
3. **다음 행동이 응답에 없다.** DR3 순서의 "다음 대전에서"(조건부 다음 행동, C-O3)를 시안에서 뺐다. 제품 핵심 줄이라 서버 필드(`next`)가 생기면 결론·원인 다음에 다시 넣는다(DESIGN.md 컴포넌트 "다음 행동" 그대로).
4. `rolls` 문자열은 화면에서 쓰지 않는다(`rolls_k`만 씀). 계속 보내도 되지만 문구를 바꿔도 화면은 영향 없다.

### web/ 임시 표시와 다른 점

- `.chip.check`: 노란 점선 → **경고색 실선** + " · 확인"(점선은 빈 칸 전용).
- `.basis-note`: 경고색 → **`muted`**, 클래스는 `.basis-src` 둘째 줄로 합침.
- `.bases`: 720px 안 2열 → **1200px 이상에서만 1104px로 넓힌 2열, 그 아래는 우선순위 순 상하 배열**(위 P1).
- 결론 h1에 `summary` 전체를 넣지 않는다. 2026-10-23 web/ 화면에서 h1이 4줄 문단이 되어 답이 3초 안에 읽히지 않았다. `headline`(제안 1)이 오기 전까지는 `summary`의 첫 문장만 h1에 두고 나머지는 h1 아래 14px `muted` 문단으로 내리기를 권한다.
- 띠 옆 글자는 `rolls`(긴 문장)가 아니라 `rolls_k`로 "16번 중 k번". 긴 문장 때문에 조건 칸이 좁아졌다.

### 확인하지 않은 것

- `web/` 실제 화면은 열어 보지 않았다(시안만 검수). 옮긴 뒤 `/design-review`로 본다.
- 스크린 리더 실제 낭독은 확인하지 않았다(aria 속성만 넣음).
